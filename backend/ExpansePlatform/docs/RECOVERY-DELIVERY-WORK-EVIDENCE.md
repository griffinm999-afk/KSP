## Read-only discovery before writes

Production has BackgroundResourceProcessing 0.2.7, its DLL/XML and local integration dependencies; the original dev GameData has no BRP directory. The installed BRP `BackgroundResourceProcessor` exposes `Inventories`, `GetInventoryById`, current resource states, `UpdateBackgroundState`, `MarkDirty`, and vessel changepoint/state/save/restore events. Whole-vessel `AddResource`/`RemoveResource` is unsuitable for explicitly selected depot members and no-ops for a loaded vessel. BRP inventory `FlightId` maps to KSP `Part.flightID`/proto `flightID`, while M2 registration stores `persistentId`; an adapter must resolve the mapping and prove stock-part ownership before selected-tank writes. Exact per-inventory mutation, dirty notification, catch-up, save/load and rollback are **unverified**. An apparent removal-allocation concern in decompiled code needs a known-tank dev test; no production API behavior is claimed from inspection alone.

Direct `Assembly-CSharp.dll` decompilation shows the full `GamePersistence.SaveGame` path: `CurrentGame.Updated` first constructs `FlightState`, whose constructor calls each `Vessel.BackupVessel()` (loaded vessel becomes a new `ProtoVessel`), then `ScenarioRunner.GetUpdatedProtoModules()` calls each live ScenarioModule.Save/OnSave through a new `ProtoScenarioModule`, then `onGameStateSave(ConfigNode)` fires. Later `Game.Save` copies those already-captured Scenario and Flight nodes, fires `onGameStateSaved(Game)`, and `ConfigNode.Save` writes the file. The alternate `Game.Save` conditional onGameStateSave branch is normally skipped because Updated initialized `additionalSystems`. BRP loaded-vessel SaveVessel runs on the normal onGameStateSave event **after both captures**. `FlightState.Save` has no exposed event callback. Earlier shorthand in this ledger reversed the ordering and an intermediate note omitted the Updated step; this full chain supersedes both. Neither event is a pre-capture mutation guard, and no post-write durable callback was identified. The selected saved capsule is authority, but physical tank/capsule save-cut ordering remains a Stage 3b proof. The dev game's Managed directory lacks `netstandard.dll`; a launcher-owned facade is not evidence the KSP process can resolve a netstandard domain DLL. Root accepted one domain source compiled for `net472` and `net8.0`; actual net472 loading was observed in the Stage 3a isolated game run.

### Provider boundary for unloaded and distant vessels

The implementation and read-only source review keep physical writes limited to an unpacked, loaded active Flight vessel. `BackgroundResourceProcessor` is a `VesselModule`, and its inventory key is the KSP part `flightID` plus nullable `moduleId` and resource name; a runtime no-write probe confirmed this mapping for two selected parts. The BRP `ResourceProcessor.ApplyInventories` path reconciles each inventory using `Amount + (PartResource.amount - OriginalAmount)` and then writes the clamped result to the part resource. Its `UpdateState(updateSnapshots:true)` path can take `Snapshot.amount` as its baseline and reset both `Amount` and `OriginalAmount`; BRP inventory `Save` persists `Amount` and `OriginalAmount`.

These paths mean that editing proto inventories or snapshots for an unloaded/distant vessel cannot be treated as equivalent to the proven loaded transaction. We have no verified bounded provider transaction or save-cut for that state. `GoOnRails` in the accepted physical run produced `packed=true, loaded=true`, so it did **not** exercise unloading. The unloaded/remote capability remains held, and no distant transfer claim is made. In loaded scenes, the BRP `BackgroundResourceProcessor` background-update/shadow refresh and resource add/remove entry points are guarded against operation on a currently loaded vessel; no alternative remote writer is approved by the current evidence.
