## Feasible first offer

Offer one explicitly selected Duna **Cultivate(S)** investment, alongside import-only and compare options. It uses the existing agriculture package, two actual harvesting hoppers configured for Substrate/Water, paid finite Fertilizer deliveries, a named physically assigned Scientist with native BotanySkill, real power/fuel/heat and existing registered physical inventory boundaries. Quotes may recommend imports when this investment is uneconomic, but local investment must remain an executable reviewed choice when its complete bill and qualification can be satisfied.

The installed `Duna_Agriculture.cfg` declares Cultivate(S) nominal inputs per second: Substrate 0.0026, Water 0.0026, Fertilizer 0.000026, ElectricCharge 5.49 and Machinery 0.000002, with required installed Machinery 100. Its nominal Supplies output is 0.00026/s, or 5.616 units per 21,600-second Kerbin day before native efficiency/thermal/specialist terms. That unadjusted estimate alone cannot cover the currently demonstrated 23 visitors plus two arrivals at the managed one-unit/person/day support rate. Never assume a specialist bonus, multiply it twice, or call this observed throughput.

Installed `000_USITools/Patches/TraitsAndEffects.cfg` gives Scientist BotanySkill. Runtime must still require the actual crew's `HasEffect` and exact workplace membership, not only a trait label. The current agriculture manifest already bills a Scientist workplace, building/material/labor and physical startup contents: 300 Water, 300 Substrate, 100 Fertilizer, 100 Machinery and 120 Supplies. The latter is real physical inventory, not automatically owned support reserve.

The existing three-hopper package uses Harvesting375 options. Each selected Substrate/Water option consumes **five WOLF points**, not physical input units. Its installed output ratios are nominal physical rates; its native consumer must actually connect and allocate those points before activation. The current manifest's ordinary recipe `Inputs` does not encode WOLF option `InputResources`; production catalog extraction must include the installed option vector explicitly. The existing raw-resource WOLF purchase engine can build paid Power/raw-vein dependencies, but two independent quotes from one depot-before snapshot cannot be composed by assuming they share untouched Power. Use one combined demand vector and one whole-depot before/after allocation authority.

Direct WOLF Supplies extraction is not the first supported offer: the installed LifeSupport250 part and Supplies option are `NEEDS[USILifeSupport]`, and this colony currently has an explicit absent-USILS managed support owner. A source CFG on disk does not prove a loaded AvailablePart. Tundra gypsum-to-Fertilizer is a second optional investment: nominal Gypsum 0.0272/s, EC 29.92/s, Machinery 0.00004/s, installed Machinery requirement 2000, Fertilizer output 0.0136/s; full package, Engineer, gypsum allocation, power/fuel/maintenance bill must determine its economics.

## Proposed bounded contract

* Add nullable `ColonyFoundingIntent.Production` (`ColonyProductionIntent`) with `Mode` = `importOnly|compare|localInvestment`, installed hash-bound `RecipeId`, `PackageCount` bounded 1..4 and `ReviewHorizonSeconds` bounded 1..30 Kerbin days. Empty/null preserves old approval hashes and behavior. Free-text charter Purpose never selects a recipe or authorizes spending.
* Add environment-only `ColonyProductionRecipe` catalog (maximum 16) binding actual loaded template/part/module/option identities, configuration hashes, physical nominal input/output vectors, native required inventory, native experience effect, reconfiguration resource costs, WOLF consumer point vectors and background adapter identity. Bound vectors to 16 resources; reject missing/unknown native providers. Catalog facts are estimates and installed identities, not measured output promises.
* Add quote-bound `ProductionInvestments` (maximum four) with exact recipe/template hashes, named building lines, named worker transfer/recruitment claim, compound WOLF purchase/depot vector, native bay changes, physical startup input/fuel/machinery buffers, recurring input reserve terms, full funds/material/labor and delayed/zero-output downside. Link to existing plan building/import/worker/fund claims rather than inventing a second procurement ledger.
* Add saved per-investment claim with immutable reviewed terms and deterministic child IDs, observed actual facility/part/module IDs, state `planned|building|inputs|configuring|observing|operational|held|cancelled` and before/after witnesses. Native recipe/hopper effects must have separate durable attempted/unknown status; a restored unknown allocation or bay change is held, never retried as a new purchase or silently credited.
* Add environment-only `ColonyProductionObservation`: exact context/module/recipe, observed interval, actual inputs/outputs and native multiplier boundary, measured physical tank deltas (including competing consumers), qualified worker/power/input/background reasons. Label nominal estimates, measured net tank change and actual provider production separately. A net tank gain does not by itself attribute gross recipe output if another producer or consumer shares it.

Suggested pure interfaces: `QuoteProductionInvestment(state,colonyId,intent,env)` and compound `QuoteWolfSupplies(state,colonyId,demandVector,env)`. Existing `QuoteFoundingPlan(...,intent)` incorporates chosen investment lines and the complete purchase maximum. The reviewed approval remains one command and authorizes deterministic construction, paid inputs, named worker placement, native option configuration and activation children. Normal standalone production review/approval can reuse this exact quote/claim mechanism later.

## Runtime sequence and accounting

1. Reserve the complete bill including zero-output import fallback; create real plots/buildings, pay and place through current construction ownership. Preserve all existing crew and facilities.
2. Purchase compound finite WOLF raw-source dependencies once; retain exact paid module/depot allocation receipts. Configure/connect each actual hopper through reviewed installed native APIs with durable before/after consumer and option witnesses. No virtual point-to-stock conversion.
3. Deliver owned startup inputs only through exact registered inventory transfers and qualified service paths. Machinery remains the actual installed maintenance target; an enabled pure warehouse reserve is not an installed Machinery target. Apply actual paid native bay reconfiguration resource costs once, or use an explicitly hash-bound preconfigured new package whose native load/readback proves that initial option.
4. Transfer the reviewed named qualified ordinary worker into the real production cabin; do not require residency/home designation before commissioning or infer a bonus from a remote job label.
5. Qualify full recipe demand, actual connected input access, endurance/heat and native background mapping. Call installed native start/swap/connect API, not direct `IsActivated` writes. Observe final PrepareRecipe output as well as inputs and native efficiency exactly once. Existing passive observer currently captures only inputs/requirements and needs a narrowly scoped output observation extension.
6. Native MKS/WOLF/BRP owns production. Only existing exact physical-to-owned stock transfer receipts increase owned stock or release a reserved import. Until then, throughput forecast retains the full import downside and automatic reserve policies continue under reviewed finite supplier/freight/cash constraints.

The current agriculture package has a native Pu238 generator whose required local Pu238 threshold exceeds its startup fuel amount. That can throttle actual power. The offer must re-quote correct costed fuel/endurance or a revised certified package; never advertise its nominal generator output as reliable supply. Root owns current power correction. Prepared-recipe BRP support exists for USI_Converter; active packed/unloaded recipe, input and output readback is still an actual native acceptance requirement.
