# Recovery and delivery interface freeze

September 26, 2026. This is Sol's package boundary for the 3a-first implementation under `RECOVERY-AND-DELIVERY-DESIGN.md`. The domain semantics and acceptance gates remain in that design. All names and bounds here are implementation contracts between the two Luna packages; changes that alter save authority or effect ordering return to Astra for review.

## File ownership

* Host/Core worker exclusively edits `src/Expanse.Domain/`, `src/Expanse.Clock.Core/`, `src/Expanse.Clock.Host/`, and `tests/` for wire types, canonical state transitions, SQLite, Host loops and deterministic tests. It may add Host-specific dev tools under `dev/Expanse.Recovery.HostFixture/`.
* Bridge/Manager worker exclusively edits `src/Expanse.WorldBridge/`, `src/Expanse.Clock.Manager/`, and KSP dev harness source under `dev/Expanse.Recovery.KspFixture/`. It consumes the domain assembly and frozen wire types; it does not edit the Host worker's paths.
* Sol owns `docs/`, `tools/`, `package.ps1`, package integrity, dev installation backups, integration, and evidence. The site worker owns the existing Site source and publication before returning to bridge/Manager work.

The shared domain is a dependency-light KSP-independent library compiled from **one source project** for both `net472` and `net8.0`. The local KSP game Managed directory has no `netstandard.dll`; the facade under the separate launcher is not a reliable game probe. Root accepted dual targeting instead of a separate netstandard-only launch. Copy only the net472 domain output to the isolated dev KSP plugin directory and prove it loads in the 3a integration run. These are two runtime-specific DLLs from one rules source, not a claim of binary-identical assemblies. No JSON/SQLite/Unity/KSP packages enter the domain assembly. The bridge stays `net472`/C# 7.3; Host and Manager stay .NET 8.

Frozen public API names: namespace `Expanse.Domain`; public settable POCOs with parameterless constructors for bridge-side compatibility. `AcceptedState` has `SchemaVersion`, `WorldId`, `CheckpointId`, optional `ParentCheckpointId`/`ParentBranchId`, `Revision`, `AcceptedSequence`, `CompactionWatermark`, `Counter`, and arrays `Depots`, `Routes`, `Rules`, `Shipments`, `Receipts`. `AcceptedStateCodec.Serialize`, `Deserialize`, `ComputeHash`, `Validate` own canonical bytes and hash. `RecoveryCapsule` has `SchemaVersion`, `WorldId`, `StateBytesBase64`, `StateSha256`. Stage 3a operation kind is `CounterIncrement` with `CounterDelta`. The effect DTO names are `EffectAttach`, `EffectPoll`, `EffectProposal`, `EffectReceipt`, `EffectIdle`, and `EffectNeedAttach`, with `EffectEnvelope` carrying protocol version and message type. Existing `ClockViewClient.GetSnapshotAsync(TimeSpan? timeout = null, CancellationToken cancellationToken = default)` remains source compatible.

## Canonical accepted state

`AcceptedState` is the single immutable accepted projection. Schema 1 contains nonempty `worldId`, `checkpointId`, optional parent checkpoint/branch ancestry, `revision` and `acceptedSequence` as nonnegative Int64, `compactionWatermark` as nonnegative Int64 no greater than `acceptedSequence`, nonnegative Int64 test `counter`, bounded active depot/route/rule/shipment records, and up to 32 detailed receipts. Stage 3a leaves route/rule/shipment arrays empty; later stages fill them without adding another source of ownership. The existing `DepotRegistryModule` owns the world GUID and member table. A recovery capsule whose `worldId` disagrees with the loaded registry is unavailable for writes, never silently repaired from the Host.

Receipt identity is `(worldId, commandSequence, operationId, payloadHash)`. `OperationIdentity.Create(worldId, commandSequence, clientRequestId)` deterministically binds an operation ID to its world/sequence/retry identity; both sides validate it. Accepted sequences increase by one. A retained matching receipt returns its recorded outcome; a reused ID or sequence with a different hash is a conflict. A sequence at or below the compaction watermark cannot execute: return `alreadySettledCompacted` without inventing an outcome. The Host must not create a new operation ID for a client retry. A rejected/held preflight does not advance accepted state. The 32-receipt tail never silently evicts: at capacity, hold new effects until exact-revision/hash compaction. A faulted uncertain physical operation blocks its endpoint and is retained in the accepted projection or a bounded fault record before any more writes.

Compaction is itself one accepted command. It requires the exact current revision/hash and a validated prior target watermark; it advances `acceptedSequence` and revision once, leaves the test counter unchanged, derives a deterministic checkpoint, removes only receipts at or below the target watermark, and appends its own compact receipt. Capacity preflight must account for that replacement. A duplicate compact resolves through its retained receipt or the explicit compacted outcome and never executes as a fresh command with a reused sequence.

Canonical hashing uses explicit typed field tags and length-prefixed UTF-8 bytes, fixed field order, sorted ID collections where order is semantically irrelevant, and invariant little-endian integers. Operation quantities use signed 64-bit micro-units for exact intended ledger deltas; only strictly positive manifest quantities are accepted. **Never quantize or rewrite existing KSP double tank stock** into these units. A gateway may conservatively floor observed usable stock/capacity to micro-units for planning without altering the tank value; ordinary fractional stock is supported. At effect time the gateway re-reads actual finite before values, rejects a proposed delta that cannot be represented accurately at that double magnitude, and records/checks actual after-minus-before differences against a specified tiny tolerance. A rounded request must never mint or destroy cargo. Canonical hashes are SHA-256 over typed bytes, never JSON text, locale formatting, or dictionary iteration order. A copied `AcceptedState` is validated and hash-checked before use.

The recovery ScenarioModule saves one `EXPANSE_RECOVERY` node with `schemaVersion=1`, `worldId`, `stateBytesBase64`, and `stateSha256`. The decoded state is bounded to 36 KiB; the complete encoded capsule text is bounded to 48 KiB, leaving frame room. Check final UTF-8 bytes, including Base64/JSON escaping, before proposing an effect or compaction. `OnSave` writes the already accepted immutable state and never waits for the Host. `OnLoad` atomically replaces all pending/derived state, including an absent node; an unknown/corrupt node is copied raw and writes remain disabled. The transient `runId` is generated on confirmed load/revert and is **not** persisted. Conservative extra run fencing on ordinary KSP load callbacks is permitted if accepted state survives and stale commands reject.

## Effect synchronization channel

Preserve the existing clock `clockSample` and read-only `getSnapshot` v1 protocol. Add a separate v1 effect pipe with default name `ExpanseFoundations.Effects.v1.<Environment.UserName>`. The isolated dev name must have the exact prefix `ExpanseFoundations.Effects.dev.<Environment.UserName>.` followed by a validated token. Only the Host creates a current-user-only server; the bridge initiates as a client on a background worker. Each frame is a little-endian UInt32 byte length followed by 1..65536 UTF-8 JSON bytes. Reads handle partial frames and enforce size before allocation. No worker touches Unity objects; no game-thread wait on pipe, SQLite, or acknowledgement.

One persistent duplex connection uses one framed request followed by exactly one framed response, sequentially on its single bridge worker. The first request is `effectAttach`, answered by a direct `effectIdle` or `effectNeedAttach`. Subsequent `effectPoll` requests run about once per real second and may coalesce; responses are a direct `effectProposal` (not wrapped), `effectIdle`, or `effectNeedAttach`. An `effectReceipt` gets `effectIdle` only after full accepted-state verification and durable Host settlement; otherwise `effectNeedAttach` fences work. Core names are `EffectsProtocol.DefaultPipeName` and `EffectsProtocol.CreateDevPipeName(token)`; dev tokens match `[A-Za-z0-9_-]{1,64}`. Host accepts `--effects-pipe`, `--command-pipe`, and `--data-dir` overrides. JSON uses direct camelCase DTO fields. These discriminated message types all have `protocolVersion=1`:

1. Bridge `effectAttach`: install namespace, save folder, `worldId`, transient `runId`, clock `sessionId` and observed `loadEpoch`, KSP process ID/start UTC ticks, `checkpointId`, accepted revision/sequence/watermark/hash, capability flags, and the full current capsule. Host validates the capsule against the fields and the **live matching clock sample** before offering work. An unavailable/corrupt/loading context advertises a reason and cannot receive a command.
2. Bridge `effectPoll`: same session/load-epoch/context identity and accepted prefix, without a full capsule. Host responds with `effectIdle`, `effectNeedAttach`, or one `effectProposal`. The worker places at most one proposal in a non-overwriting main-thread mailbox. Polls are bounded and may coalesce; proposals/receipts may not.
3. `effectProposal`: immutable `operationId`, `clientRequestId`, `commandSequence`, `worldId`, `runId`, clock session/load epoch, expected revision/hash, payload hash, operation kind and typed payload. The Host must commit a SQLite `prepared` row **before** sending. Only one prepared proposal per writable world context is offered at once.
4. Bridge `effectReceipt`: repeats operation and session/load-epoch identity/hash and records `accepted`, `duplicate`, `alreadySettledCompacted`, `rejected`, `held`, or `faulted` plus actual applied UT, quantities, accepted revision/sequence/state hash when relevant, and a bounded reason. The worker sends only a result produced on the game thread. Host settles or archives its prepared row in a SQLite transaction and acknowledges receipt. **Before offering another proposal, Host must possess verified accepted state**: either the complete capsule in the receipt, a fresh `effectAttach`, or a deterministic reducer applied to the exact actual receipt with hash equality. Prefix/hash alone cannot project an unknown outcome. On disconnect, the bridge's accepted capsule is the recovery witness; retry uses the same operation ID.

Every effect message is fenced by install namespace, save folder, world ID, run ID, live clock session/load epoch and accepted prefix. Save folder is a namespace hint, never world authority. Context mismatch causes `effectNeedAttach` or rejection, never an implicit cross-run retry. An unexpected backward UT fences writes pending reattachment. Host persists a bounded writer lease for the attached world: bridge process ID, process start UTC ticks, executable path/install, session and run. It verifies those against the local process and the current clock sample. A different session cannot take over while the prior verified process lives, even if pipes disconnect; PID reuse is resolved by start identity. An unresolved prior owner yields a visible ambiguous-writer hold, never a timeout guess. The same process can reattach with a new run/epoch after matching live clock context. Synthetic tests inject a process-liveness provider. A transient disconnection leaves the read-only clock operational.

## Host files and Manager commands

SQLite lives only under an explicit Host data directory; dev tests pass a separate directory. Use `Microsoft.Data.Sqlite` available locally and `PRAGMA user_version` migration from an empty database, with one serialized writer/transaction at a time. Tables retain world/branch/run attachment, prepared immutable commands, settled receipts and archived history. The KSP capsule, not the newest DB row, selects the active prefix. On a missing database, rebuild operational active state from `effectAttach` and label detailed history unavailable. Backups use SQLite's supported backup API rather than file copy during writes.

Add a separate current-user-only Host command pipe with default `ExpanseFoundations.Commands.v1.<Environment.UserName>` and validated dev override. Its bounded v1 `submitCommand` carries stable `clientRequestId`, current viewed world/run context and a typed command; the Host returns pending/accepted/rejected with the same ID and operation ID if prepared. Repeated submissions with the same ID and typed payload resolve to the same operation; same ID with changed payload rejects. Manager never writes the DB or save directly. For 3a only a dev-only counter command is exposed; production UI does not offer fuel actions before 3b/4 gates. Later send-once and schedules enter this same command service.

For stage 4 migrate the M2 `DEPOT_REGISTRY` schema 1 single depot to a schema 2 bounded depot array without changing that depot/world/member identity. No automatic whole-vessel enrollment. Prevent member overlap, and return explicit unavailable reasons when a source or destination is not safely observable. The bridge/Host file boundary uses stable depot IDs and membership revisions rather than vessel names. Runtime support for BRP/unloaded resources is capability-gated and cannot be inferred from a generic `PartResource` or proto amount.
