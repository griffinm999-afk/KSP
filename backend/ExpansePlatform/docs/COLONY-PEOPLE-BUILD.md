# Residents and modeled passenger transport

Source: `ColonyPeopleState.cs`, `ColonyPeopleEngine.cs`, `ColonyPeopleCodec.cs`, and `ColonyRuntime.People.cs`. Small coordinated hooks add the people environment/state list, command dispatch, funds completion, chronological boundary and runtime provider calls. The companion app receives bounded current roster/seat/route metadata and offers reviewed recruitment/departure plus explicit existing-crew assignment.

## Ownership and operation rules

- KSP's actual roster owns named Kerbals. The saved `RosterId` is the actual roster name key; changing it externally requires explicit reconciliation. Ordinary Available Crew or named Applicants may be recruited. Arrival converts the same actual Applicant to Crew; it does not create a second random Kerbal or invoke stock `HireApplicant` and charge twice. Fare and recruitment fee are the explicitly configured modeled-service balance rule.
- Residents reserve operational certified homes and actual part-seat capacity. Physical visitors also occupy seats. Existing visitors are never silently designated residents; Jeb, Bill, Bob, Val and hero crew require an explicit assignment field. Fresh landed site presence includes people outside adopted buildings; tourists/rescue roster records count as visitors rather than ordinary recruits.
- A job requires the registered actual work part, an operational facility, matching trait and physical occupancy. Pure domain assignment does not move a person, change a PartModule or invent a worker bonus. The actual KSP crew/trait system retains authority.
- Passenger operations reserve finite configured concurrent seats and shared funds. Fare is debited through the existing witnessed funds provider. Saved fare and lead time survive route configuration changes after payment. A transport timer only queues the physical crew effect; it never declares an arrival complete.
- A before-witness and applying phase precede physical crew changes. The same save/epoch, actual roster type/status, actual part mapping and exactly-one membership must be read back before completion. Any uncertain post-callback result is held, never blindly repeated. The KSP save boundary persists both colony and roster/part data; unsaved changes are not claimed crash durable.
- Unpaid reservations may be cancelled without modifying the actual roster or refunding unknown payments. Started/paid transport cannot be cancelled by a speculative refund. Queued/full/missing arrivals retain the actual person and home reservation. There are no automatic deaths.
- Immigration requires commissioned Expanse resident support, currently sufficient unreserved colony-owned Supplies for the charter reserve days, and qualified home utilities. No pre-adoption support debt is created. A visiting astronaut's explicit resident assignment changes designation rather than creating new physical demand.

## Runtime providers

Loaded crew uses installed `Part.AddCrewmemberAt`/`RemoveCrewmember`, rebuilding the vessel crew list and spawning the unpacked presentation where appropriate. Anchored-packed does not require unanchoring. Unloaded crew uses the actual ProtoPart crew/name lists plus ProtoVessel crew APIs; both mappings are inspected and read back. Unloaded housing additionally requires the facility's qualified background support. The provider requires explicit template home craft IDs, exact actual placement markers, sorted actual persistent home-part IDs and `ColonyEngine.HomeMappingHash` seal. Only deployed Habitat MK2 home cabins count; hubs, airlocks, control and work seats do not. `CertifiedHousingPart` may add an additional trusted gate, but cannot promote an unsealed work seat. Loaded native part identity uses KSP-normalized `KKAOSS.Habitat.MK2.g`; unloaded cabins require initialized deployed animation state as well as sealed mappings. Installed method semantics were inspected locally: `ProtoVessel.AddCrew` adds its crew list/rebuilds counts; `ProtoPartSnapshot.RemoveCrew` removes corresponding crew and name entries. This supports the implementation decision but is **not runtime certification**. Loaded/packed/unloaded save/reload and trait propagation still require isolated KSP evidence.

The provider performs at most one physical crew effect per tick and rotates ready effects, so an unavailable home cannot starve another colony. Roster and world observation limits are explicit (2,048 roster records/vessels); metadata limits are also enforced by the pipe codec. Work and frame time must be measured at the planned 100-facility/200-person scale. These limits are conservative implementation bounds, not measured performance claims.

## Explicit route configuration

There is no invented default or free passenger route. GameDatabase nodes named `EXPANSE_COLONY_PASSENGER_ROUTE` must provide `id`, `name`, `body`, `fare`, `recruitmentFee`, `travelSeconds`, `concurrentSeats`, `qualified`, `evidence`, and `developmentOnly`. Terms are hashed in the provider and included in the app review. A `developmentOnly=true` route requires the read-only `colony-development-authorization.cfg` gate: exact canonical installation root, exact disposable `ColonyBuild-*` save leaf, and exact unique explicit development pipe. A dev-name prefix alone is insufficient. Its qualification flag is an explicit commissioning assertion; set it only as part of the verified route qualification procedure. Missing/unqualified routes produce a useful blocker.
